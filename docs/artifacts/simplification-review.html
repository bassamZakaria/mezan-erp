Decisions taken

Sixteen findings were answered by a judgement rather than by code — a choice between two defensible readings, or a deliberate refusal to build what the reviewer asked for. Each is recorded here with what was decided, why, and what would reverse it, so the next person meets the reasoning instead of the silence.

  1. Does the approver-is-not-the-submitter rule apply to an admin too?
    Yes — the admin bypass does not lift it. A bypass is a shortcut past the ROLE a step names, not past the separation the step exists for; letting "*" through would mean the control stops at exactly the account most likely to hold both permissions. It costs nothing in practice, because an admin's own submission never becomes pending in the first place — startApproval grants it outright — so the only request an admin can be the submitter of is one they raised before being promoted.
    Nothing. A single-user shop that wants no separation configures no chain, which is the honest way to say so.
  2. What should the new discount ceiling default to?
    100 — the ceiling ships off. One company's idea of a safe discount is not another's, and a limit nobody chose would refuse documents a tenant has always been allowed to raise. What does not depend on configuration is a giveaway: a zero unit price or a full discount always needs sales.price.override, because there is no reading under which selling for nothing is ordinary. So the control bites out of the box where the act is unambiguous, and waits for a decision where it is not.
    Nothing; a tenant sets a number in الإعدادات when they have one. If it turns out every install sets the same figure, that figure is the better default.
  3. Sales invoices are paged in SQL — but «مفتوحة» and «متأخرة» are not. Why the exception?
    Because no column holds them. Both are functions of the remaining balance, which is the invoice total less payments less return credits — three sources, one of them another module's. Faking a column would put a derived figure in the books where a stale copy could disagree with the ledger, which is the defect class this codebase already has three of. The two chips resolve over the filtered set and page afterwards; every OTHER filter is SQL by then, so what is loaded is that chip's own set rather than the table.
    Reverse it if a materialised remaining-balance column is ever added for its own reasons — it must never be added FOR this.
  4. Should the shortcuts sheet become a routed page?
    No — it stays an overlay. Two reviewers disagreed. A cheat sheet you must leave your work to read is a 119th route, and the complaint underneath the finding was discoverability, not addressing. It got a visible help button in the chrome instead, beside the gear.
    Reverse it if support tickets show people wanting to link someone to the shortcut list.
  5. Delete the g-chord, as two reviewers recommended?
    Not yet — the layout bug was fixed first. The chord's letters come from the English group key while the label is Arabic, and they silently reassign whenever the nav is restructured. But ? and ⌘K were dead on the Arabic layout, so nobody had used the chord enough to have an opinion. Fix the keymap, then look again at what people actually press.
    Delete it if the letters still drift after the navigation freeze, or pin them in a static map beside navGroupSpecs.
  6. Delete the four unreachable inventory report routes, or wire them up?
    Wire them up. The reviewer offered both. They were routed, chunked, icon-mapped and named in both catalogues — everything except a nav entry, which reads as an omission during a restructure rather than a decision to retire them. Four working screens became reachable for one line of config, and the command palette picked them up for free because it builds from the nav.
    Nothing; if they are genuinely unwanted, removing them is now a visible product choice rather than a silent one.
  7. Two mounts served the seven statements. Fix the slice, or delete the duplicate?
    Both. Fixing only the slice would leave two implementations free to diverge again — which is what happened the first time. The duplicated routes are gone and the statements hub reads the surviving mount; the local helper that remains, feeding the account drill-down, was corrected to the same slice with a comment saying why.
    Nothing.
  8. The year-end close zeroes the P&L. Move the entry's date, or exclude it from reports?
    Exclude it. Dating a closing entry on the last day of the year it closes is correct accounting, and moving it would trade a reporting bug for a ledger one. It now carries sourceDocType: "YEAR_END_CLOSE" and the two performance statements skip it. The balance sheet deliberately does not, because retained earnings is precisely what the close moved — and the cash-flow opening and closing balances keep every entry, since the close touches no cash account and that tie-out must stay exact.
    Nothing.
  9. A bounced cheque made the aging ladder and the dashboard tile disagree by 1,750. Which was right?
    Neither — they meant different things, so the meaning was settled. Bouncing reclassifies GL 1320 → 1360 and leaves AR alone: the money is still owed and still has to be chased. The tile summed 1105 and 1110 only. Since both screens claim to answer "what do customers owe us" for collections, 1360 joined the tile rather than the ladder dropping the debt. The D37 regression guard, which asserts the two agree, is what forced the question.
    Reverse only if "receivables" is redefined product-wide to mean trade AR alone — in which case bounced cheques need a surface of their own.
  10. Where should the expired-stock block sit?
    On the issue, not on the ledger. A hard stop at the ledger would also block the two things a shop must be able to do with expired goods: write them off through an EXPIRY adjustment, and return them to the supplier. postIssue refuses; adjustments and transfers do not, so moving a bad lot to quarantine still works. The check reads the FEFO head only — layers are consumed expiry-first, so if the first is good nothing behind it can be expired.
    Add a tenant policy if a client genuinely needs to sell past expiry; nothing in Egyptian practice suggested one.
  11. Three purchasing approval gates are advertised and never enforced. Enforce, or stop advertising?
    Stop advertising, for now. Enforcing them means a pending status, a workflowRequestId and a release path on three bespoke document types that do not go through DocumentService — a larger change than this pass. The two inventory gates, which do go through it, were genuinely enforced and verified against a seeded backend. The three purchasing ones are marked enforced: false and the config screen now reads «غير مُفعَّل بعد». A chain a tenant believes is holding spend when it is not is a worse control than none.
    Build the hold-and-release path; the marker is a placeholder, not an answer.
  12. Sessions in memory, or persisted?
    In memory. A desktop edition is one process; a restart asking the shopkeeper to sign in again is not a hardship, and it means a stolen database file carries no live sessions. Only the token's SHA-256 is stored even there, and SHA-256 rather than scrypt is deliberate: the token is 256 random bits, not a human-chosen secret, so there is nothing to brute-force and this runs on every request.
    Persist them when a session has to survive a restart — a till mid-shift, say — and encrypt that table.
  13. The branch/warehouse scope still travels on the request. Is that not the same hole?
    No, because it can only narrow. Choosing one branch in the topbar is a real user action and the request has to carry it. The granted scope comes from the session, and an id outside that grant is dropped rather than honoured — the same rule the return-quantity defect taught: a limit the caller supplies is not a limit.
    Nothing. Widening from a header would be the original defect again.
  14. The seed, smoke, coverage and the scenario harness all declared x-permissions: "*". Exempt them, or make them sign in?
    Make them sign in. A test path that skips authentication stops testing the thing that broke. They log in as the seeded admin now; the seed additionally mints a session per identity, because HR leave derives the employee from the caller and the approval scenarios need named non-admin actors — which is exactly the impersonation the server stopped accepting.
    Nothing.
  15. Approver-is-not-submitter: fixed?
    Not yet — but it is now possible. The check itself is still missing from the workflow engine. What changed is that it can now mean something: the submitter and the approver's roles both come from resolved sessions, so a comparison would be between two facts rather than two headers the same person could write.
    Add the comparison in workflow/gate.ts; the identities are trustworthy now.
  16. Should role presets ship with the duplicate-role action?
    No — deliberately left to you. "Cashier" and "Sales Rep" are names for permission sets somebody has to choose, and choosing them in code would bake one company's idea of a cashier into every install. Duplicating an existing role gives the same relief without the guess.
    Ships as soon as the preset contents are specified.

The shortcut surface

You asked about the shortcut page. It exists — as an overlay, not a route — and it is reachable three ways. Two of those three are broken on an Arabic keyboard, and the sheet advertises a feature that does nothing.

What is actually there

ShortcutsOverlay renders a two-column cheat sheet: seven global keys on one side, and on the other the g-chord jumps derived live from the navigation tree. It is wired from the gear menu (shell.utility.shortcuts), from the command palette (cmd-shortcuts), and from the bare ? key. The overlay itself is fine. Everything around it is not.

Three defects, all verified in source all three fixed

«؟» is not ?. useGlobalShortcuts.ts:129 tests event.key === "?". On the Arabic layout Shift+Q emits U+061F. The file already contains latinLetter(), written precisely so g s survives an Arabic keyboard by falling back to event.code — that fallback is never applied to ?.

⌘K is dead on the same layout, for the same reason, in a different file: CommandBar.tsx:30 keeps its own document listener outside the "single global keydown listener", and matches event.key only. ⌘N and ⌘S work, because they go through the fallback. So the two doors that survive on an Arabic keyboard are the gear menu and nothing else.

j/k/Enter row navigation does not exist. emitListNav dispatches mz:list-nav; a repository-wide grep finds the event name in exactly two places, both of them the emitter. No listener was ever written. The handler calls preventDefault() first, so the keys are swallowed rather than passed through — and the sheet still advertises «J+K — تحريك التحديد في الجدول».

What to do with it

The panel split on whether it should become a page. Keep it an overlay — a 119th route you must leave your work to read is not an improvement — but fix the three defects, add one visible help control in the chrome so it is not folklore, and put Kbd hint chips on the create and save buttons, which is what the UX spec meant by "discoverable, not folklore".

On the g-chord: two reviewers independently recommended deleting it. Its letters are picked from the English group key while the user reads Arabic labels («البيع» → g s), the mapping is written down nowhere but the sheet, and it silently reassigns itself whenever the nav order changes — which it has, repeatedly, this week. ⌘K already reaches every one of those destinations by Arabic name. If it stays, pin the letters in a static map beside navGroupSpecs.

A green gate that was not measuring anything

Worth recording beside the documents, because it is the same class of problem. pnpm smoke only fails on a 5xx or a 404. When the authentication fix landed and 193 of its 199 read surfaces began answering 403, it printed ok 403 for each one and reported "smoke passed". The suite that exists to prove the app is reachable would have certified an app nobody could reach.

It signs in as the seeded admin now and treats 401 and 403 as failures — an unauthenticated smoke run proves nothing. The same fix went to check:seed. While chasing it, a second cause surfaced: demo-seed.ts carried its own private copy of ADMIN_HEADERS beside the shared one, which is why the first attempt at the fix appeared to do nothing.

The lesson generalises past this repo: a gate's pass condition has to be "the thing worked", not "the thing did not explode". Everything between those two is where a false green lives.
