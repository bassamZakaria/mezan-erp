Rebuilding the interface, not repainting it

The app doesn't feel overwhelming because it looks dated. It feels overwhelming because it is organised around how the software was built rather than around the work an Egyptian accountant, cashier or storekeeper actually does in a day — and the person who opens it every morning is not technical.

Twelve ground rules fix the audience. Thirteen decisions then cover the whole surface: what the navigation is organised around, what the landing screen contains, where reports and settings live, the visual language, how deep the pass goes, how the rail behaves, where buttons sit, whether work happens in drawers or on pages, what the app says back when you save or make a mistake, how wide and dense a page is, how somebody learns it without training, how a list gets narrowed, and where the product's distinctiveness lives. Pick one option per decision and the rebuild has a spec.

What I found in the running app

The overwhelm is measurable

I drove the seeded build rather than reading the code. These are the specific things doing the damage — each one is a structural or content problem, not a styling one.

8

Eight equally-weighted buttons across the top of the dashboard

فاتورة جديدة, سند نقدي, استلام بضاعة, فاتورة مشتريات جديدة, أمر شراء جديد, عرض سعر, إضافة صنف — all the same size, same colour weight, no primary. Eight choices is not a call to action, it's a menu the eye has to parse.

7

Seven panels on the dashboard with no ranking between them

KPI tiles, a follow-up list, a balance-scale illustration, an expense donut with a ten-row legend, an aging matrix, top-selling items and an activity feed all render at the same visual weight. Nothing tells the eye where to land, so the eye reads everything — which is the definition of overwhelming.

117

Every destination lives at the same depth in one module tree

The tree mirrors the product's own architecture: 14 groups, 22 sub-sections. A cashier has to learn that تحصيل lives under المبيعات while سند قبض lives under الخزينة — two different doors for one mental task.

4

Filter chips that show zero and stay on screen

The sales-invoice list renders eight status chips; four of them read 0. Empty filters occupy the same space as useful ones and teach the user to stop reading the row.

1

Developer copy shipped into the product

The sales-invoice page prints its own service class as the page subtitle: SalesInvoiceService (ترقيم + قيد محاسبي + صرف مخزوني). It reads as a description of the code, to a user who wants a description of the screen.

5

KPI rows that wrap into an orphan

Five tiles in a four-column grid leaves one stranded on a second row, so إجمالي المتبقي — arguably the number that matters most on that screen — reads as an afterthought.

430px

Real documents are entered through a phone-width slot

62 screens edit inside a fixed 430px slide-over. An invoice with line items, quantities, discounts and tax has less width than a phone held sideways — and the list behind it is dimmed and unreachable while it's open. There's no URL for the record either, so nobody can send a colleague a link to an invoice.

0

Nothing tells the user their work was saved

No toast, no confirmation dialog, no loading skeleton exists anywhere in the product. 54 screens each invented a local setStatus message instead, so "did that go through?" gets a different answer — or none — on every screen. For a confident developer this is a nuisance; for a shop owner it's the reason they save the same invoice twice.

∞

Rows as wide as the monitor

<main> sets padding but no maximum width. On a wide screen the customer name sits on one edge and the amount on the other, and the eye has to travel the whole span to connect them.

Ground rules · not optional

The person using this every day is not technical

These aren't a decision to make — they're constraints that bind every decision below. A shop owner or a storekeeper who never trained on software has to be able to open this and work. Each rule is checkable, so it can be enforced by review rather than by good intentions.

Three options further down are already ruled out by these: D3 as a default look (dense rows, small targets), F2 hover-flyout navigation (hover is not a discoverable affordance), and any pattern that hides a needed control behind a collapsed toggle — which is what the filter bar does today.
Rule 01

Every control is at least 44px tall

Big enough to hit without aiming, on a trackpad or a touch till.

Now: filter chips are 31px.

Rule 02

Never colour alone

Every state carries colour and a shape or icon and a word. Roughly one in twelve men cannot separate the red and green this app uses for overdue and paid.

Rule 03

One numeral system, chosen once

Arabic-Indic or Western, set per user, never mixed on a screen.

Now: the aging matrix heads its columns ٣٠ / ٦١-٩٠ and fills its cells 34,130.88.

Rule 04

Label by the task, then the accounting term

«استلام فلوس من عميل» first, «سند قبض» underneath. The formal word stays — it just isn't the only way in.

Rule 05

Nothing appears only on hover

If it can be clicked it can be seen. Row actions, menus and tooltips all have a visible, tappable trigger.

Rule 06

Irreversible actions say what they will do

One plain sentence naming the consequence — «سيُنشأ قيد عكسي ولن تُحذف الفاتورة» — not «هل أنت متأكد؟».

Rule 07

No English anywhere on the surface

No class names, no enum values, no untranslated errors.

Now: a page subtitle reads SalesInvoiceService.

Rule 08

Empty is never blank

Say what isn't there and give the button that creates it. A blank panel reads as a broken app.

Rule 09

Works at 125% zoom

Older eyes zoom. Nothing may overlap or scroll sideways when they do.

Rule 10

The needed control is never collapsed by default

Hide what's rarely used, never what the screen exists for.

Now: filters start collapsed; zero-count chips start visible.

Rule 11

Uniqueness is never spent on controls

A button, a field and a table behave the way every other program on the machine behaves. Distinctiveness goes into structure, typography and one signature instrument — see Decision 13.

Rule 12

Every screen survives the shop test

Someone who has never seen it should be able to name what the screen is for and what the main button does, in five seconds, out loud.

Decision 01 · Navigation

What should the sidebar be organised around?

This is the biggest lever. Nothing gets deleted in any option — everything stays reachable through search and the command palette. What changes is what a person sees before they've searched for anything.

Decision 02 · The landing screen

What should the dashboard actually contain?

Today it answers "how is the business doing?" — a question the owner asks monthly. The person who opens this app at 9am every morning is asking a different one.

Decision 03 · Content placement

Where should reports and configuration live?

Two categories are currently mis-shelved, and both push daily work further away. These are independent of each other — pick any combination.

Multiple selections allowed.

Decision 04 · Visual language

What does "futuristic and professional" mean here?

The identity — deep teal, gold, Arabic-first, tabular figures — is worth keeping. What's on the table is how surface, depth and density are expressed on top of it.

Decision 05 · Depth

How far does this pass go?

There are about 90 screens. Most of them render through shared primitives — a document list, a document detail, a form, a page header — so rebuilding those primitives improves screens nobody touches.

Decision 06 · The rail itself

How should the sidebar behave?

Separate from what's in it. Today it is a fixed 264px rail that collapses to 76px icons, with no search inside it, no pinning, and no memory of where you were. For someone who uses four screens all day, that rail is 90% dead weight.

Decision 07 · Buttons

Where do actions live on a screen?

DocumentList currently renders its actions as a plain wrapping flex row — every button the same weight, in source order. That single line of layout is what produces the eight-button pile-up, and it repeats on every list in the app.

Decision 08 · Where work happens

Drawers, or pages?

62 screens do their editing inside a 430px slide-over panel. A sales invoice with line items, quantities, discounts and tax has to fit a column narrower than a phone held sideways — and while it's open, the list it came from is dimmed and unreachable.

Decision 09 · What the app says back

Feedback, waiting, emptiness and mistakes

There is no toast, no confirmation dialog, and no loading skeleton anywhere in the product — 54 screens each invented their own setStatus message instead. For a non-technical daily user this is the single biggest source of "did that work?".

Decision 10 · The page frame

Width, density and motion

<main> has no maximum width. On a wide monitor a table row runs the full span of the screen, so the eye has to travel from a customer name on one edge to an amount on the other.

Decision 11 · Learnability

How does someone who isn't technical learn this?

This is an accounting system, and accounting vocabulary is unavoidable. What is avoidable is making the person learn the software's vocabulary on top of it. The app currently explains itself nowhere except a first-run wizard.

Decision 12 · Filtering

Are chips the right way to narrow a list?

No — and the code says why. The chips are aria-pressed buttons inside a role="tablist", so they announce themselves as one thing and behave as another. Visually they're pills, which everywhere else in software means "pick several" — but only one can be active. They render at zero. And the real filters sit behind a toggle that starts closed.

Decision 13 · Distinctiveness

Where does the uniqueness live?

Being unique and being obvious pull against each other only if the uniqueness is spent on controls. Spend it on the concept layer instead — the metaphor, the typography, one signature instrument — and the buttons can stay boringly conventional while the product still looks like nothing else on the market.

Given that the person opening this every morning is not technical, my recommendation as a set is A1 · B1 · C1 · C2 · D1 · E1 · F1 · G1 · H1 · I1 · J1 · K1 · L1 · M1 — reorganise around the work rather than the modules, make the landing screen a worklist, re-shelve reports and configuration, keep the identity but go dark-first, rebuild structure and primitives before individual screens, let the rail learn what this person uses, rank every screen's actions to exactly one primary, give documents real pages, ship one shared feedback system with undo and plain-Arabic confirmations, cap the content width with a comfortable default, wrap the five daily tasks in guided flows, replace filter chips with named views, and build the balance itself into a component the whole product uses.

On uniqueness: M1 is the answer I'd defend hardest, because it's the only choice here that makes the product more distinctive and easier for a beginner at the same time. Everything conventional — buttons, fields, tables, menus — stays conventional on purpose. That's what buys the freedom to be unusual where it counts.

The one I'd most expect you to overrule is D1 — dark-first is my read of "futuristic", but if your customers work in bright shops with the screen near a window, D2 is the better commercial answer and costs less to build. M2 would pair with it naturally.
